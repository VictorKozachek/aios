# Приёмка M0 на реальном железе (AM5) — чеклист

Часть приёмки M0; автоматическая проверка в QEMU — в [M0.md](M0.md).
Цель: на AM5-плате `v0.1` грузится с USB, печатает карту памяти / CPUID / ACPI
в serial и framebuffer, проходит проверку памяти и W^X. Критерии —
`docs/PLAN-M0.md` §3, `docs/SPECIFICATION.md` §12.1, FR-1.1.

> M0 ничего не пишет на диск и в прошивку. Восстановление после сбоя — снятие
> питания и повторная запись USB, поэтому «кирпич» на M0 невозможен, если не
> менять настройки прошивки вручную (риск R16: не писать в NVRAM/SPI).

## 0. Что нужно

| Что | Требование |
|---|---|
| Плата | AM5, UEFI class 3 (например, X670E/B650), Secure Boot выключается |
| CPU | Ryzen 9 (MVP — 9950X или аналог), 16+ ядер |
| RAM | 64 ГБ DDR5 (по спеке MVP) |
| Экран | HDMI/DP-монитор, умеет 1920×1080; для проверки второго разрешения — 800×600 (EDID-эмулятор или второй монитор) |
| USB | флешка ≥ 1 ГБ (образ ESP ~64 МБ), порт на задней панели |
| Serial | USB-UART 3.3 В (CP2102/FT232) + Dupont; на плате — колодка COM |
| Камера/телефон | фото экрана и секундомер |
| Восстановление | вторая машина для записи USB, запасная плата + CH341A (риск R16) |
| Доступ | физический доступ к кнопке питания и Clear CMOS |

## 1. Подготовка образа и USB

На машине разработки (из корня `v0.1`):

```bash
make test
make image
shasum -a 256 build/aios.img
```

**Ожидаемо:** `make test` зелёный, `make image` создал `build/aios.img`;
хеш записан в отчёт.

Запись на USB (macOS; `diskutil list` — найти флешку, `diskN` — её номер):

```bash
diskutil list
diskutil unmountDisk /dev/diskN
sudo dd if=build/aios.img of=/dev/rdiskN bs=1m
diskutil eject /dev/diskN
```

**Ожидаемо:** `dd` завершился без ошибок, флешка извлечена. Проверка чтением:

```bash
# размер образа в байтах
img_bytes=$(stat -f%z build/aios.img)
sudo dd if=/dev/rdiskN bs=1m count=$((img_bytes / 1048576 + 1)) 2>/dev/null \
  | head -c "$img_bytes" | shasum -a 256
```

**Ожидаемо:** хеш совпадает с хешем `build/aios.img`.

## 2. Настройки UEFI (один раз)

| Настройка | Значение | Зачем |
|---|---|---|
| Secure Boot | **Disabled** (Other OS) | наш Limine не подписан (M5 — свои ключи) |
| CSM / Legacy | **Disabled** | грузимся только UEFI |
| Fast Boot | Disabled | чтобы видеть меню загрузки и USB |
| Boot order | USB первой (или F11/F8 при старте) | загрузка с флешки |
| Above 4G Decoding | Enabled | адресация MMIO/памяти как в спеке |
| Serial/COM port | Enabled (если есть пункт) | вывод в COM1 |

**Ожидаемо:** настройки сохранены (F10), плата перезагрузилась; версия BIOS
записана в отчёт (она входит в манифест дистрибутива, риск R14).

## 3. Подключение serial

1. Плата выключена. Подключить USB-UART: `GND↔GND`, `TX↔RX`, `RX↔TX`,
   уровень 3.3 В (не 5 В).
2. На ноутбуке:

```bash
ls /dev/tty.usbserial-* /dev/tty.SLAB_USBtoUART 2>/dev/null
screen /dev/tty.usbserial-XXXX 115200
# выход из screen: Ctrl-A, затем K
```

Альтернатива: `picocom -b 115200 /dev/tty.usbserial-XXXX`.

**Ожидаемо:** после включения платы в терминале идут строки Limine, затем
`=== AIOS kernel ===`. Если терминал пуст — проверить перекрёст TX/RX, порт COM
в UEFI и скорость 115200 8N1.

## 4. Загрузка с USB и маркеры

1. Вставить USB в порт на задней панели (не через hub).
2. Включить плату, в boot-menu (F11/F8/F12 — по модели) выбрать
   `UEFI: <флешка>`.
3. Запустить секундомер в момент нажатия кнопки питания.
4. Остановить секундомер на строке `--- memory map ---`; записать время.

**Ожидаемо (serial, те же строки, что в QEMU):**

```text
limine: Limine <версия>
limine: base revision requested 3
--- memory map ---
HHDM base: 0x…
RSDP: 0x…
CPUs: N            (N ≥ 1, соответствует числу ядер CPU)
TSC: …
boot: ok, halting
```

| Проверка | Ожидаемо |
|---|---|
| Время от power-on до `--- memory map ---` | **≤ 5 с** (`docs/PLAN-M0.md` §3) |
| Карта памяти | ≥ 3 записи (usable/reserved/acpi/mmio), сумма usable ≈ 64 ГБ |
| `CPUs: N` | соответствует числу физических/логических ядер |
| `RSDP: 0x…` | ненулевой адрес |
| `TSC: …` | ненулевое значение |
| `PANIC:` | отсутствует |

## 5. Память и W^X

**Ожидаемо (serial):**

```text
mem: alloc 1 GiB ok
mem: free ok
w^x: execute from heap -> page fault
```

| Проверка | Ожидаемо |
|---|---|
| Выделение 1 ГиБ страницами | `mem: alloc 1 GiB ok`, ядро продолжает работу |
| Освобождение | `mem: free ok`, счётчик занятой памяти вернулся |
| Исполнение из кучи | `w^x: execute from heap -> page fault`, обработчик `#PF` печатает дамп, паники и зависания нет |
| Накладные расходы ядра | по счётчику `mem:` — ≤ 1 % RAM (≤ 0.64 ГБ при 64 ГБ); число записать в отчёт |

Если маркер `w^x: …` отсутствует — реализация T4b не сдала критерий, задача
возвращается (см. [M0.md](M0.md) §7).

## 6. Экран (framebuffer)

1. Сфотографировать экран после `boot: ok, halting`.
2. Сверить текст с serial-логом: те же строки (критерий
   `docs/ARCHITECTURE.md` §3).
3. Проверить два разрешения: 1920×1080 и 800×600. Если монитор не умеет
   800×600 — использовать EDID-эмулятор или второй монитор; записать, чем
   проверяли.
4. Для T7 (если влит): на экране сплэш `AIOS · SkyNet v0.0.1` + git-хеш
   совпадает с `git describe`; строка инициализации не пустая.

**Ожидаемо:** фото экрана приложено к отчёту; версия/хеш совпадают; при
отсутствии framebuffer (не наш случай на AM5) — текстовая строка в serial.

## 7. Восстановление после сбоя

M0 не пишет на диск и не меняет NVRAM, поэтому восстановление — всегда
перезагрузка/перепрошивка USB. Действия по симптомам:

| Симптом | Что проверить | Ожидаемый результат |
|---|---|---|
| Нет загрузки, UEFI не видит USB | Secure Boot off, CSM off, порт на задней панели, перезаписать USB | плата грузится с флешки |
| Чёрный экран, serial пуст | TX/RX местами, COM в UEFI, скорость 115200 | в терминале идут строки Limine |
| Limine есть, ядра нет | образ/ядро: пересобрать `make image`, сверить хеш USB | `=== AIOS kernel ===` |
| `PANIC:` в serial | снять последние 40 строк serial, приложить к отчёту; питание выключить | после перезагрузки — снова загрузка |
| Зависание без вывода | питание кнопкой (5 с), повторить; если повторяется — QEMU-воспроизведение и карточка | загрузка в QEMU воспроизводит дефект |
| Сбросились настройки UEFI | Clear CMOS (кнопка/перемычка), заново §2 | настройки применены, версия BIOS в отчёте |
| Плата не стартует после экспериментов | не трогать SPI/NVRAM; CH341A + запасная плата (риск R16) | плата восстановлена внешним программатором |

**Запрещено на M0:** прошивать BIOS из нашей ОС, писать в NVRAM, включать
Secure Boot со своими ключами (`sbctl` — M5), трогать NVMe-разделы.

## 8. Отчёт по железу

Заполнить и приложить к отчёту M0 ([M0.md](M0.md) §5):

```text
board:        <модель>, BIOS <версия>, дата BIOS
cpu:          <модель>, ядер/потоков
ram:          <ГБ>, <частота>
usb:          <порт>, <флешка>, sha256 образа
monitor:      <модель>, <разрешение>
serial:       <адаптер>, <путь к логу>
photo:        <файл>
time to memmap: <с> с (порог 5 с)
memory:       alloc 1 GiB ok / free ok; ядро <МБ>, доля <%
w^x:          page fault обработан, паники нет
screen:       1920×1080 — ok/нет; 800×600 — ok/нет
recovery:     не потребовалось / действия <…>
```

## 9. Техника безопасности

- Отключать питание перед подключением serial и USB.
- ESD-браслет или разрядка корпуса перед работой с платой.
- Не оставлять плату с открытым доступом к SPI при включённом питании.
- Держать запасную плату/программатор: M0 — первая загрузка на «живом» железе
  (риск R16), цена ошибки — выезд с программатором.
