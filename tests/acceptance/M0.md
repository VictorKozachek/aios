# Приёмка M0 «Металл» — чеклист и сценарии

Документ описывает, **как принять веху M0**: что проверяем, чем, какой результат
считается ожидаемым. Он собран из `docs/PLAN-M0.md` §3, `docs/SPECIFICATION.md`
§12.1 и `docs/ARCHITECTURE.md` §3, §4. Приёмку проходит человек или агент
(роль `verifier`), шаг за шагом, без домыслов: у каждого пункта есть команда и
ожидаемый вывод.

Проверка на реальном железе — отдельный чеклист: [M0-hardware.md](M0-hardware.md).

## 0. Что считается приёмкой M0

M0 принята, когда:

1. все пункты §2 (QEMU) пройдены на ветке версии `v0.1` после слияния задач M0,
   автоматический скрипт `tests/acceptance/qemu-accept.sh` завершился кодом `0`;
2. все пункты [M0-hardware.md](M0-hardware.md) пройдены на AM5-плате (демо-железо);
3. в §5 заполнен отчёт: дата, git-хеш, машина, числа, ссылки на логи и фото;
4. CI на `v0.1` зелёный, а негативная проверка детектора (§2.6) доказывает, что
   регрессия загрузки валит проверку, а не проходит молча.

Приёмка — это демонстрация, а не «код написан» (`docs/SPECIFICATION.md` §12.2).

## 1. Предусловия

| Что нужно | Проверка | Ожидаемо |
|---|---|---|
| Ветка версии с влитыми задачами M0 | `git log --oneline -1` | на `v0.1`, рабочее дерево чистое (`git status --short` пуст) |
| rustup-тулчейн и target | `$HOME/.cargo/bin/rustup target list --installed` | есть `x86_64-unknown-none` |
| QEMU | `qemu-system-x86_64 --version` | ≥ 11.x (на M0 — 11.1.3) |
| OVMF | `ls "$(brew --prefix qemu)/share/qemu/edk2-x86_64-code.fd"` | файл существует |
| mtools | `command -v mformat mcopy` | обе команды найдены |
| Limine | `make image` не должен падать на поиске `BOOTX64.EFI` | образ собран; путь задаётся `LIMINE_DIR` |
| Ядро собирается | `make kernel` | `target/x86_64-unknown-none/debug/aios-kernel` существует |
| Тесты форматов | `make test` | `cargo test -p memfmt` зелёный, ядро собирается |

Если на месте нет Limine: `brew install limine` (или `make image LIMINE_DIR=/path/to/limine-binary`).

## 2. Автоматическая проверка в QEMU

Все команды выполняются из корня рабочего дерева `v0.1`. Скрипт не правит ядро
и не требует ручной сборки: он сам вызывает `make image`, поднимает QEMU,
сохраняет логи и проверяет маркеры.

### 2.1 Сборка

```bash
make test          # cargo test -p memfmt + сборка ядра под target
make image         # FAT-ESP: Limine + limine.conf + /boot/kernel
ls -l build/aios.img target/x86_64-unknown-none/debug/aios-kernel
```

**Ожидаемо:** обе команды завершились кодом `0`; `build/aios.img` и ядро на
месте. При ошибке — приложить вывод команды к отчёту, приёмка дальше не идёт.

### 2.2 Загрузка до памяти и маркеры контракта

```bash
tests/acceptance/qemu-accept.sh
```

**Ожидаемо:** в конце вывода `M0 QEMU acceptance: PASSED`, код возврата `0`.
Логи и снимок экрана: `build/acceptance/serial.log`, `build/acceptance/debugcon.log`,
`build/acceptance/framebuffer.ppm`.

Скрипт проверяет маркеры (точные подстроки в serial-логе):

| Маркер | Что доказывает |
|---|---|
| `=== AIOS kernel ===` | управление дошло до ядра |
| `boot: entry reached (_start)` | `_start` по протоколу Limine выполнен |
| `limine: Limine <версия>` | загрузчик ответил и его версия известна |
| `limine: base revision requested 3` | запрошен протокол base revision 3 |
| `--- memory map ---` | карта памяти получена и печатается |
| `HHDM base: 0x…` | HHDM-смещение получено |
| `RSDP: 0x…` | корень ACPI получен |
| `CPUs: N` | число CPU известно, `N ≥ 1` |
| `TSC: …` | частота/значение TSC получено |
| `boot: ok, halting` | ядро дошло до конца сводки и не упало |

Дополнительно: в карте памяти ≥ 3 записи; `CPUs` положительное; `PANIC:` в
логе отсутствует; в `debugcon.log` есть тот же баннер (канал `0xE9` работает).

**Критерий времени:** от запуска QEMU до строки `--- memory map ---` — **≤ 5 с**
(`docs/PLAN-M0.md` §3). Скрипт печатает измеренное значение в миллисекундах.
На TCG-эмуляции (Apple Silicon) допускается зафиксировать фактическое число;
превышение 5 с — провал пункта, даже если все маркеры на месте.

### 2.3 Три канала диагностики

| Канал | Проверка | Ожидаемо |
|---|---|---|
| Serial (COM1) | `grep -c '=== AIOS kernel ===' build/acceptance/serial.log` | ≥ 1 |
| debugcon (порт `0xE9`) | `grep -c '=== AIOS kernel ===' build/acceptance/debugcon.log` | ≥ 1 |
| Framebuffer | `build/acceptance/framebuffer.ppm` (открыть как изображение) | текст на экране совпадает с serial |

Скрипт автоматически проверяет serial и debugcon и сохраняет снимок
framebuffer (PPM — «сырой» формат QEMU). **Ручной шаг:** сконвертировать и
сверить, что на экране те же строки, что в `serial.log` (критерий
`docs/ARCHITECTURE.md` §3: «если упало после framebuffer — framebuffer + serial +
debugcon»):

```bash
sips -s format png build/acceptance/framebuffer.ppm --out build/acceptance/framebuffer.png
open build/acceptance/framebuffer.png
```

### 2.4 Память и W^X

Эти маркеры — **контракт приёмки M0** для T3/T4b (см. карточки задач): ядро
обязано напечатать их в serial при штатной загрузке в QEMU.

| Маркер | Что доказывает |
|---|---|
| `mem: alloc 1 GiB ok` | аллокатор физической памяти выдал 1 ГиБ страницами |
| `mem: free ok` | выделенное освобождено, счётчики вернулись |
| `mem: kernel used <N> KiB` | счётчик занятой ядром памяти — вход для метрики ≤1 % RAM (§12.1) |
| `w^x: execute from heap -> page fault` | исполнение из кучи поймано page fault, а не выполнено |

**Ожидаемо:** все четыре строки есть; после `w^x: …` ядро продолжает работу
(обработчик `#PF` печатает дамп, паники нет), финальная строка
`boot: ok, halting` присутствует, `PANIC:` отсутствует.

Если реализация T4b напечатала другие формулировки — это не «пройдено
молча»: формулировки меняются в задаче T4b вместе с этим файлом и
`tests/acceptance/qemu-accept.sh`, иначе приёмка не воспроизводима.

Проверить вручную:

```bash
grep -E 'mem: alloc 1 GiB ok|mem: free ok|mem: kernel used [0-9]+ KiB|w\^x: execute from heap -> page fault' \
  build/acceptance/serial.log
```

### 2.5 Формат сегмента совпадает с документом

```bash
make test
grep -n "SEGMENT_HEADER_LEN\|RECORD_HEADER_LEN\|SEGMENT_MAGIC\|RECORD_MAGIC" \
  libs/memfmt/src/*.rs
```

**Ожидаемо:** `cargo test -p memfmt` зелёный; заголовок сегмента — 64 байта,
заголовок записи — 32 байта, magic `AIOSSEG1` и `0x41494F53` (на диске
`53 4F 49 41`), `pad[12]`/`pad[2]` — как в `docs/ARCHITECTURE.md` §5.2.
Тест «обрезка на каждом байте» и «порча середины → damaged» входят в
`cargo test -p memfmt` (см. карточку T5).

### 2.6 CI ловит регрессию загрузки

```bash
ls .github/workflows/ci.yml
grep -nE 'cargo (check|test)|make (test|image|smoke)|qemu' .github/workflows/ci.yml
command -v gh >/dev/null && gh run list --branch v0.1 --limit 5
```

**Ожидаемо:** workflow собирает ядро, гоняет host-тесты, собирает образ и
запускает QEMU-smoke; последний запуск на `v0.1` — зелёный.

**Негативная проверка детектора** (обязательна, выполняется локально, ядро не
правится — берётся образ без ядра):

```bash
dd if=/dev/zero of=build/acceptance/empty.img bs=1m count=8
tests/acceptance/qemu-accept.sh --negative --image build/acceptance/empty.img --timeout 15
```

**Ожидаемо:** `negative: OK — no kernel marker …` и код `0`: проверка **падает**
на образе, который не грузит ядро. Если негативный режим вернул `1` — детектор
сломан, и зелёный CI ничего не доказывает; это провал приёмки.

## 3. Приёмка на реальном железе

Полный чеклист: [M0-hardware.md](M0-hardware.md). Кратко: образ на USB,
Secure Boot выключен, загрузка с USB, serial-лог снят, маркеры §2.2 совпадают,
время до карты памяти ≤ 5 с, экран показывает тот же текст, восстановление после
сбоя — перепрошивка USB (M0 ничего не пишет на диск).

## 4. Метрики `docs/SPECIFICATION.md` §12.1: что проверяется в M0

В M0 проверяются только метрики, у которых уже есть измеряемая подсистема.
Остальные — заявленные цели следующих вех; в приёмке M0 они **не проверяются**
и не считаются провалом.

| Метрика (§12.1) | Цель | В M0? | Чем мерим |
|---|---|---|---|
| Загрузка до строки карты памяти | ≤ 5 с | **да** | `qemu-accept.sh` (мс), на железе — секундомер от power-on |
| Накладные расходы ядра по памяти | ≤ 1 % RAM (≈0.6 ГБ при 64 ГБ) | **да, на железе** | `mem: kernel used N KiB` из serial после T4b, делить на 64 ГБ |
| Загрузка до готовности API | ≤ 10 с (без весов) | нет — M1/M4 | появится вместе с API |
| Скорость генерации tok/s (все модели) | 3–20 tok/s | нет — M4 | встроенный бенчмарк |
| Prefill, TTFT, TTFT возобновления | ≥100 tok/s / ≤500 мс / ≤2 с | нет — M4 | `/metrics` |
| Байт NVMe на ход, hit-rate памяти, экономия токенов | ≤8 МБ / ≥90 % / ≥20 % | нет — M2/M6 | `/metrics` |
| Бюджет сервисов, потребление в простое | ≤4 ГБ / ≤30 Вт | нет — M1+ | `/metrics`, ваттметр |
| Стабильность 30 суток | без перезагрузки | нет — M2+ | soak-тест |
| 1000 обрывов питания без потери данных | 1000 | нет — M2 | скрипт-тест ФС |
| Покрытие policy engine тестами | 100 % правил | нет — M6 | CI |

## 5. Отчёт о приёмке

Заполняется по итогам; копируется в карточку задачи приёмки (`#009`) и в
`docs/` при выпуске. Пустые «Факт» — приёмка не пройдена.

```text
M0 acceptance report
date:           2026-…-…
git:            v0.1 @ <sha> (+ git describe)
machine:        <плата>, BIOS <версия>, CPU <модель>, RAM <ГБ>
QEMU:           qemu-system-x86_64 <версия>, OVMF <путь>
run:            tests/acceptance/qemu-accept.sh  -> PASSED, <N> checks
boot to memmap: QEMU <мс> мс; железо <с> с
memory:         alloc 1 GiB ok, free ok; занято/свободно <числа>, доля ядра < %>
W^X:            execute from heap -> page fault (обработано, без паники)
channels:       serial ok, debugcon ok, framebuffer ok (фото <файл>)
format:         cargo test -p memfmt — <N> passed; §5.2 сверен
CI:             <run url/номер>, зелёный; negative check — OK
hardware:       см. M0-hardware.md, все пункты пройдены
known issues:   <список или «нет»>
```

## 6. Что осознанно не входит в M0

Из `docs/PLAN-M0.md` §4: SMP-инициализация (AP поднимает Limine, per-CPU
структуры — M1), планировщик, каналы, userspace, драйверы NVMe/NIC, сеть.
Всё это M1–M3 и в приёмке M0 не проверяется.

## 7. Если проверка не прошла

1. Зафиксировать пункт, команду, фактический вывод и ожидаемый — в карточку
   задачи (не в этот файл): `bin/task-move.sh <id> in-progress --role verifier
   --note "что не сходится, чем воспроизвести, что ожидалось"`.
2. Приложить логи: `build/acceptance/serial.log`, `debugcon.log`,
   `framebuffer.ppm`; на железе — фото экрана и serial-лог.
3. Не «доливать потом»: задача возвращается исполнителю, приёмка повторяется
   после исправления (`docs/WORKFLOW.md` §3).
