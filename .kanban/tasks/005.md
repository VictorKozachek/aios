## Задача

T4b: интеграция `libs/mmcore` в ядро — реальная память вместо абстракции.
База ветки: `task/004` (в ней уже есть `BootInfo` из T2b и IDT/обработчики из T3).

### Что сделать

1. **Физический аллокатор**: по `BootInfo.memmap` собрать диапазоны usable и отдать их
   `mmcore::buddy::BuddyAllocator`. Не копировать логику — вызывать библиотеку.
2. **Таблицы страниц**: инициализировать свои 4-уровневые таблицы, включить их (CR3),
   учитывая, что Limine уже отдал HHDM (`BootInfo.hhdm`) — kernel продолжает работать
   по этим адресам, поэтому HHDM должен сохраниться в новом наборе.
3. **Отображения**: MMIO — uncached, framebuffer — write-combined, куча ядра — RW+NX
   (W^X: исполнение из кучи запрещено).
4. **Куча ядра**: регион из аллокатора, простой linked-list аллокатор поверх mmcore.
5. **Обработчик #PF**: связать с IDT из T3 — печатать адрес (`cr2`), причину и halt.
   Это и есть проверка W^X: исполнение из кучи должно давать внятный page fault.
6. **Метрики в лог**: сколько памяти отдано аллокатору, сколько свободно, размер кучи.

### Приёмка

- `make smoke` остаётся 11/11;
- в логе QEMU: `memory: total X MiB, free Y MiB, heap Z KiB`;
- тест `AIOS_MEM_TEST=1`: выделить 64 МиБ страницами, освободить, проверить, что счётчик
  свободного вернулся к исходному;
- тест `AIOS_MEM_TEST=wx`: вызвать страницу из кучи как код → `EXCEPTION #PF cr2=...` и halt;
- `cargo check --target x86_64-unknown-none` и clippy без новых предупреждений.

### Важно

- Прерывания не включать (как в T3).
- `libs/mmcore` не менять — только использовать; не хватает API — опиши в отчёте.
- Границы: `kernel/src/mm/**`, `kernel/src/main.rs` (инициализация), `kernel/Cargo.toml`
  (зависимость mmcore, lock обновить cargo).
