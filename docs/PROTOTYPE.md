# Прототип «схемы»: модель, память, воркспейсы, консоль

**Версия:** 0.1 · **Дата:** 2026-11-09

Задача этого прототипа — **отработать схему работы с моделью до того, как она
переедет в ядро**. В ядре сейчас есть загрузка, консоль и примитивы CPU; нет
хранилища, сети и инференса. Ждать M4 несколько месяцев, а понять, как должна
работать связка «модель + память + воркспейсы + консоль», нужно сейчас.

Поэтому: прототип живёт на хосте (macOS arm64, позже тот же бинарник в Linux-VM),
но **пишется на тех же принципах и с теми же форматами**, что заложены в
[ARCHITECTURE.md](ARCHITECTURE.md) §5: сегментный лог (`libs/memfmt` уже влит),
факты с провенансом, детерминированный retrieval, каталог возможностей.

---

## 1. Что проверяем

| Гипотеза | Как проверяется |
|---|---|
| Модель можно поднять локально и отвечать на простые промпты | консоль: вопрос → потоковый ответ |
| Сессия переживает перезапуск без перечитывания истории | сегментный лог + checkpoint, `resume` |
| Память даёт провенанс, а не «магию» | у каждого факта — источник, автор, уверенность |
| Retrieval детерминирован и не жрёт токены | счёт «сколько символов попало в контекст» |
| Воркспейсы разделяют работу | у `home` и `work` свои факты, индексы и права |
| Консоль удобна человеку | REPL в стиле харнесса: сессии, команды, статус |

## 2. Компоненты

```
prototype/
  modeld/     — адаптер модели: ollama сейчас, llama.cpp/свой движок позже
  memory/     — сегменты, факты, индекс, retrieval (использует libs/memfmt)
  console/    — REPL: воркспейсы, сессии, команды, статус
  api/        — HTTP API (OpenAI-совместимое подмножество), позже
```

Границы ответственности — как в будущем ядре: консоль не знает про модель,
модель не знает про память, память не знает про транспорт.

## 3. Модель

Первый бэкенд — **ollama** (`qwen2.5:0.5b`), потому что нужен быстрый цикл.
Адаптер прячет его за нашим интерфейсом:

```rust
trait ModelBackend {
    fn info(&self) -> ModelInfo;                  // имя, контекст, квант
    fn generate(&self, req: &GenRequest) -> Result<GenStream>; // потоковые токены
    fn count_tokens(&self, text: &str) -> usize;  // для бюджета контекста
}
```

Позже на место `OllamaBackend` встаёт `LlamaCppBackend`, затем `AiosEngine` —
без изменений в консоли и памяти.

## 4. Память (по проекту из ARCHITECTURE §5)

| Уровень | Что делает прототип |
|---|---|
| Эпизодическая | сегментный лог на `libs/memfmt`: каждое сообщение, вызов, решение |
| Семантическая | факты `{subject, key, value}` с провенансом, скоупами и TTL |
| Индекс | BM25 по сегментам и фактам; перестраивается сканом, без LLM |
| Контекст | билдер с бюджетом: системная часть, закреплённые факты, хвост сессии, извлечённые эпизоды |

Ключевой принцип из спеки: **модель не решает, что читать** — решает
детерминированная retrieval-политика; модель может попросить `mem.search`
как отдельную возможность.

KV-снапшоты в прототипе **не делаем** — это работа движка в ядре (M4). В
прототипе переиспользование префикса обеспечивает сам ollama.

## 5. Воркспейсы

```
~/.aios/workspaces/
  home/   config.toml  memory/  files/  sessions/
  work/   config.toml  memory/  files/  sessions/
```

- **Воркспейс = скоуп памяти + свои файлы + свои права.**
- `home`: досуг, личные заметки, без доступа к рабочим файлам.
- `work`: код, документы, дизайн.
- Переключение — командой в консоли; текущий воркспейс виден в приглашении.
- Права: файлы одного воркспейса не видны из другого (проверяется тестом).

## 6. Консоль (в стиле харнесса)

```
aios[work] > найди в памяти, что мы решали про формат снапшотов

  [mem] 2 записи: ARCHITECTURE §5.4 (decision), T5-отчёт (fact)
  [ctx] 1 842 токена: system 400 · facts 300 · tail 900 · retrieved 242

  Снапшот адресуется парой (SnapshotKey, prefix_hash)…
```

Команды первого этапа:

| Команда | Что делает |
|---|---|
| `/ws <name>` | переключить воркспейс |
| `/new`, `/resume` | новая сессия / вернуться к прошлой |
| `/remember subject key = value` | записать факт (автор — человек) |
| `/memory <query>` | поиск по памяти с провенансом |
| `/forget <id>` | удалить факт (с подтверждением и аудитом) |
| `/status` | модель, токены, размеры памяти, воркспейс |
| `/quit` | выход |

## 7. Во что превратится

| Прототип | В ядре |
|---|---|
| `modeld` (ollama) | `modeld` (свой движок, M4) |
| сегменты через `libs/memfmt` | те же сегменты, `storaged` |
| факты и индекс в памяти процесса | они же в `storaged`, с диском |
| консоль-REPL | консоль на framebuffer/serial |
| воркспейсы как каталоги | воркспейсы как скоупы сессий |

## 8. Критерии готовности прототипа

1. `cargo run -p aios-console` → приглашение, воркспейс `work`.
2. Вопрос на русском → потоковый ответ модели.
3. `/remember` → факт сохранён; после перезапуска консоли факт на месте.
4. Вопрос, требующий памяти → факт попадает в контекст, и это видно в `/status`.
5. RAG по текстовому файлу из `files/` → ответ ссылается на фрагмент.
6. Воркспейсы не видят файлы и память друг друга.
7. Всё логируется в сегменты; сессию можно `/resume`.

## 9. Чего в прототипе нет

Мультипользовательности, сети наружу, шифрования, KV-снапшотов, GPU-offload,
Эмбеддингов (только BM25), произвольных инструментов (только каталог возможностей
с `mem.search`).
