# Рабочий процесс: ветки, слияния, релизы

Правила ниже — не бюрократия, а способ не потерять работу: каждая ветка имеет
ровно одного владельца, каждое слияние — одну причину, каждый релиз — проверенный
дистрибутив.

## 1. Ветки

| Ветка | Назначение | Кто пишет | Слияния внутрь |
|---|---|---|---|
| `main` | релизы. Только то, что выпущено | никто напрямую | merge из `develop` после проверки дистрибутива, затем тег `vX.Y.Z` |
| `develop` | интеграция. Сюда собирается всё готовое | никто напрямую | merge из `vX.Y`, когда версия готова |
| `vX.Y` | рабочая ветка версии. **Вся разработка идёт здесь** | исполнители задач | merge из `task/<id>-<slug>` |
| `task/<id>-<slug>` | одна задача = одна ветка + один worktree | один исполнитель | — (вливается в `vX.Y`) |

Правило ветки задачи: у задачи один владелец и один worktree. Никто не правит
чужие файлы; конфликт в общих файлах развязывает лид, конфликт в файлах задачи —
возврат владельцу.

## 2. Слияния

Формат сообщения:

```
[<SHORT_BRANCH>] <Что сделано>

<Зачем, что проверено, какие числа>
```

- задача → версия: `[TASK-12] Сегментный лог: запись с magic и resync`
- версия → `develop`: `[v0.1] Срез M0: загрузка в QEMU, BootInfo, paging`
- `develop` → `main`: `[release] v0.1.0`

Слияние всегда `--no-ff` (видно, что это слияние, а не «так и было»).

## 3. Что должно быть проверено до слияния в версию

| Проверка | Кто | Блокирует |
|---|---|---|
| Сборка под все целевые арх | CI | да |
| Тесты на хосте (`cargo test`) | CI | да |
| Smoke в QEMU | CI | да |
| Ревью кода (отдельная роль) | reviewer | да |
| Тест на целевом сценарии (для фич) | verifier | да |

Не проходит — карточка возвращается в работу, а не «доливается потом».

## 4. Релиз

```
v0.1 ──(готово)──▶ develop ──(тестовый дистрибутив прошёл)──▶ main ──▶ тег v0.1.0
```

1. Версия готова → merge `v0.1` в `develop`.
2. Сборка тестового дистрибутива: `make dist` → образ + манифест моделей + подписи.
3. Дистрибутив прогнан на целевом железе (загрузка, API, инференс) — критерии в
   спецификации §12.1.
4. Merge `develop` в `main`, тег `v0.1.0`, release notes: что работает, что нет,
   известные ограничения.

## 5. Кто пушит

- Агенты пушат **только свои ветки задач** и ветку версии.
- В `develop` и `main` пушит человек (или лид по явному решению) — это точка
  контроля, а не недоверие.
- Пока идёт bootstrap (репозиторий моложе первого среза), лид пушит и в `develop`:
  иначе ветки не увидеть снаружи. Это исключение, а не норма.

## 6. Доска

Видимость работы — плагин `dsh-kanban`: карточки в `.kanban/tasks/<id>.md`, таб
«Канбан» в правом сайдбаре. Карточка = задача: статус, владелец, роль, ветка,
worktree, заметки.

Колонки: `backlog → todo → in-progress → in-review → testing → ready → merged`
(`blocked` — нужен человек). Пока исполнители — агенты Agent Teams, а не отдельные
DSH-сессии, карточки двигает лид; при переходе на роли (dispatcher/worker/reviewer/
verifier) — двигают сами сессии через `bin/task-move.sh`.

## 7. Что не делаем

- Не мержим «всё подряд» в `main` ради красоты истории.
- Не держим долгоживущие ветки задач: задача живёт столько, сколько её карточка.
- Не правим чужие worktree и не «попутно» рефакторим в чужой задаче.
