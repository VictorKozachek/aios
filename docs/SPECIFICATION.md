## 1. Резюме

AIOS — операционная система, написанная с нуля, в которой:

1. **Модель (LLM) — управляющий контур системы.** Не приложение поверх ОС, а
   полноценный менеджер: она принимает намерение пользователя, планирует,
   вызывает типизированные возможности системы и отчитывается о результате.
2. **Ядро ОС не наследует Linux/POSIX.** Свой ABI, свои примитивы, своя
   файловая система, свой сетевой стек. Свобода проектировать под задачу, а не
   тащить 30 лет обратной совместимости.
3. **Вся машина — под модель.** Ресурсы (CPU, память, NVMe, сеть) распределяются
   политикой, приоритет которой — обслуживание инференса и управляющего контура.
4. **Портативность — требование первого дня.** Один код, разные архитектуры
   (x86-64 сейчас, затем aarch64/RISC-V, в пределе — собственный силикон), один
   воспроизводимый процесс сборки дистрибутива.
5. **Два равноправных интерфейса:** консоль — диалог с моделью (как рабочая
   сессия в DSH-харнессе), и защищённый API — для программ.
6. **Память — часть системы, а не файл приложения.** Сессии, контексты и знания
   живут в хранилище ОС: append-only транскрипты, снапшоты KV-cache,
   дистиллированные знания с провенансом. Возврат к разговору не перечитывает
   историю и не пересчитывает prefill.

**Формула:** *модель предлагает — ядро разрешает* (`the model proposes, the
kernel disposes`). Модель управляет, но не обладает правами root напрямую;
каждое действие проходит через политику и аудит.

## 2. Исходная идея и её разбор

Дословно (из `spec.md`):

> Данный проект представляет собой совершенно новую операционную систему,
> основным функциональным ядром будет LLM Deepseek. Цель системы, иметь все
> свободные ресурсы для работы с нейросетью. Никаких клонов линукса и их
> урезания, все делаем и пишем с нуля. Работу начнем с железа на базе AMD Райзен
> 9. Напишем наше ядро, которое будет работать с оборудованием, будет
> загружаться и при первой загрузке скачивать LLM и подымать ее, предоставлять
> АПИ по HTTP.

Уточнено владельцем при постановке задачи:

> сборка должна уметь собираться под разные архитектуры; модель управляет всем,
> взаимодействует с пользователем через консоль (как в харнессе) и через
> засекуренное API; Linux не нужен, потому что это урезанный Linux, а не новая
> система.

Разбор трёх ключевых тезисов — что каждый из них **означает технически** и чего
он **не** означает:

| Тезис | Что означает | Чего не означает |
|---|---|---|
| «LLM — функциональное ядро» | Модель — часть **управляющего контура** ОС: планирование действий, диалог, использование возможностей системы. Через неё проходят административные и пользовательские сценарии. | Не означает инференс в ring 0. Матричные умножения и загрузка весов в kernel space — источник неотлаживаемых падений и дыр в безопасности. Модель живёт в привилегированном userspace-сервисе с особым ресурсным бюджетом. |
| «Все свободные ресурсы для нейросети» | **Политика планировщика**: инференс — высший приоритет по CPU, памяти, кэшу, диску; системные сервисы урезаны до минимума. | Не означает «съесть всю память при старте». Веса, KV-cache и системный резерв размечаются заранее (admission control), иначе OOM-killer убивает саму модель. |
| «Свой kernel, не Linux-клон» | Свой ABI, свои примитивы IPC, своя ФС. Можно спроектировать примитивы под модель (сессии, инструменты, «намерения») с нуля. | Не означает «изобрести всё, включая TCP/IP и TLS» — часть протоколов рационально портировать (см. §10), иначе срок до первого демо растёт на годы. |
| «Сборка под разные архитектуры» | HAL-граница и arch-порты с самого начала; build matrix в CI; образ дистрибутива как артефакт. | Не означает «сразу поддерживать 5 платформ». Портируется **контракт**, платформы добавляются по одной. |

## 3. Позиционирование: чем AIOS не является

Границы важнее списка фич — они экономят годы:

- **Не Linux-дистрибутив.** Не BusyBox + llama.cpp в образе. Нет POSIX-слоя
  «для совместимости» — если понадобится, это отдельный необязательный порт.
- **Не десктопная ОС.** Нет браузера, офиса, игр, GUI-стека. Консоль это
  диалоговая сессия, а не TTY с bash.
- **Не облачный SaaS.** Не мультитенантность, не биллинг, не Kubernetes.
  Одна машина = один узел inference-appliance.
- **Не гипервизор.** Не VMM, не контейнеры, не поддерживаем чужие ОС как гостей.
- **Не фреймворк для агентов** в смысле LangChain. AIOS — среда исполнения:
  агентские возможности принадлежат системе, а не библиотеке.
- **Не «обучение модели».** Inference-only. Никакого обучения, LoRA, датасетов.

## 4. Проблема и мотивация

Что не устраивает в существующем положении вещей:

1. **Чужая онтология.** В Linux агент — это процесс, а модель — это файл,
   читаемый библиотекой. Примитивы (fork/exec/socket/mmap) проектировались под
   серверы 1970-х, а не под «намерение → план → действия → отчёт».
2. **Ресурсы не под модель.** В универсальной ОС инференс конкурирует с
   фоновыми демонами, обновлениями, индексаторами. Нужен приоритет инференса и
   детерминированная память под веса и KV-cache.
3. **Раздутый доверенный код.** Десятки миллионов строк, из которых нужны сотые
   доли процента. Свой минимальный kernel = меньшая поверхность атаки и полный
   контроль над тем, что происходит на машине.
4. **Нет управляющего контура.** Даже с агентом в Linux администратор остаётся
   человек с SSH и bash. Идея: администратор разговаривает с системой, а система
   сама выбирает механизмы.
5. **Портативность как чужой параметр.** Наследие Linux делает перенос на новую
   архитектуру/собственный силикон дорогим. Мы хотим, чтобы «собрать под
   riscv64/под свою плату» было работой по чеклисту.

## 6. Принципы

| # | Принцип | Практическое следствие |
|---|---|---|
| P1 | **Модель предлагает — ядро разрешает** | Управляющий контур не имеет прямого root. Любое действие = типизированный вызов возможности (capability) через policy engine. |
| P2 | **Портативность — требование первого дня** | Ни одна строка платформенного кода не живёт в ядре вне `arch/` и `platform/`. Портируемый контракт зафиксирован (§9.2). |
| P3 | **Без наследия Linux/POSIX** | Свой ABI и примитивы. Заимствуется только то, что явно решено портировать (см. §10), с фиксацией в ADR. |
| P4 | **Все ресурсы — модели, но по расписанию** | Инференс имеет приоритет; веса и KV-cache размечаются заранее; системный резерв неприкосновенен. |
| P5 | **Каждое действие аудируется** | Журнал: кто (модель/человек), что, чем разрешено, результат, стоимость. Нет действия без записи. |
| P6 | **Детерминизм там, где возможен** | Парсинг, учёт токенов, политика, проверки — детерминированный код. LLM вызывается только там, где нужна семантика. |
| P7 | **Консоль и API равноправны** | Обе поверхности — клиенты одного управляющего контура, а не разные реализации. |
| P8 | **Закрыто по умолчанию** | Сеть слушает только явно открытые порты; API требует аутентификации; инструменты модели — по белому списку. |
| P9 | **Воспроизводимая сборка дистрибутива** | `make image ARCH=…` → байт-идентичный артефакт; манифест моделей с хешами и подписями. |
| P10 | **Один камень — один контракт** | Для MVP поддерживается ровно одна плата. Драйверы пишутся под неё, не «в общем виде». |
| P11 | **Демо на каждом шаге** | Каждая веха заканчивается тем, что можно включить и показать. Иначе проект умирает на четвёртом месяце. |
| P12 | **Честность про цену** | Если что-то стоит три человеко-года, это написано в спеке, а не выясняется в конце. |
| P13 | **Память — примитив ОС, а не файл приложения** | Сессия, её контекст и знания принадлежат системе: сегментный лог, снапшоты KV-cache, дистилляция с провенансом. Возобновление сессии не пересчитывает prefill (§7.4). |

### 7.1 Что именно делает «управляющий контур»

Это ядро идеи, поэтому расписано подробно. Цикл обработки одного сообщения:

1. **Приём.** Сообщение приходит из консоли или API → сессия (идентификатор,
   права, бюджет).
2. **Контекст.** Система собирает состояние: ресурсы, сервисы, недавние события,
   память о прошлых сессиях (провенанс обязателен).
3. **План.** Модель порождает не «текст», а **структурированный план**: список
   шагов, каждый — вызов возможности из каталога (`fs.read`, `svc.restart`,
   `model.load`, `net.status`, …).
4. **Политика.** Каждый шаг проходит policy engine: разрешено ли сессии это
   действие, в каких пределах (пути, лимиты), нужен ли человек в контуре.
   Отказ — с человекочитаемой причиной.
5. **Исполнение.** Исполнитель вызывает возможность, получает типизированный
   результат (не текст), пишет в журнал.
6. **Отчёт.** Модель сводит результаты в ответ человеку или клиенту API;
   метрики стоимости (токены, время) прикрепляются к сессии.

Следствия:
- Каталог возможностей — часть ABI системы, версионируется, документируется.
  Он и есть «API системы для модели».
- Всё, что модель не может выразить возможностью, она не может сделать. Это
  главный механизм безопасности и главный источник ограничений.
- Консоль — это тот же цикл, но с человеком в роли источника намерений
  (по образцу рабочей сессии в DSH-харнессе: сессии, инструменты, подтверждения,
  расширения).

### 7.2 Ресурсный бюджет: железо → модель → скорость

Главный физический закон проекта: **скорость генерации упирается в пропускную
способность памяти, а не в FLOPs.** Замеры на реальных машинах дают устойчивые
коэффициенты полезного использования ПСП: 63–65% для dense-моделей и 34–37% для
MoE. Отсюда формулы для планирования `[ОЦЕНКА, подтверждено замерами]`:

```
dense:  tok/s ≈ 0.63 × ПСП / размер_весов
MoE:    tok/s ≈ 0.35 × ПСП / (активные_параметры × бит_на_параметр / 8)
```

**Пропускная способность памяти:**

|---|---|---|
| AM5, Ryzen 9, 2×DDR5-5600 | 2 | **89.6 ГБ/с** ← наш MVP |
| AM5, 4 DIMM (DDR5-3600) | 2 | 57.6 ГБ/с |
| Threadripper 9000, DDR5-6400 | 4 | 204.8 ГБ/с |
| TR Pro 9000 / EPYC Genoa | 8 / 12 | 409.6 / 460.8 ГБ/с |
| EPYC 9005 Turin, DDR5-6400 | 12 | 614.4 ГБ/с |

Процессор MVP — Ryzen 9 9950X: 16 ядер/32 потока, 2 CCD × 8 ядер, L3 32 МБ на
CCD, официально **до 192 ГБ DDR5**, 4- и 5-уровневые таблицы страниц (LA57),
AVX-512 полной 512-битной ширины + VNNI + BF16, **AMX отсутствует**.

Следствия, которые фиксируем как решения:

1. **Контракт MVP — 64 ГБ RAM** (решение владельца, 2026-11-09; железо: Ryzen 9,
   NVMe, RTX 3060 12 ГБ — GPU в MVP не используется). Целевой набор моделей:
   dense **14B Q4** (9 ГБ, ~6 tok/s — цикл разработки), **32B Q4** (19.9 ГБ,
   ~3 tok/s — основной кандидат), V2-Lite (10.4 ГБ, 20–25 tok/s). **V4-Flash
   (82–97 ГБ) на 64 ГБ не влезает** — открывается только после апгрейда до
   128 ГБ (2×32 ГБ), это дешёвый и обратимый шаг.
2. **671B на AM5 не влезает физически** (Q2_K = 244 ГБ при 128 ГБ). Если нужен
   именно 671B — это другая платформа (EPYC/TR Pro, 8–12 каналов) и другой
   бюджет. Решение — §15, Q2/Q3.
3. **AVX-512 полной ширины есть** на Ryzen 9000 desktop (VNNI, BF16; 4 FP-конвейера);
   AMX нет (это Intel), NPU на Ryzen 9000 нет, iGPU — RDNA2 c 2 CU, для LLM
   бесполезен (та же ПСП DDR5), ROCm на bare-metal нереален (Linux-only стек
   поверх kernel-драйвера amdgpu). Значит **GPU/NPU-offload вне MVP обоснован
   физически**, а не отложен из осторожности.
4. **Prefill дорогой.** На V4-Flash prefill ≈ 44 tok/s: 10 000 токенов промпта ≈
   225 с. Значит prompt caching (переиспользование KV-cache по префиксу) и
   честные таймауты в API — не оптимизация, а требование к дизайну (FR-7.8).
5. **Экономия памяти важнее скорости ядра.** Разница между 1.7 bpw и 2.7 bpw для
   V4-Flash — 82.5 ГБ против 96.8 ГБ, то есть «влезает в 96 ГБ» против «не
   влезает». Формат квантования — часть контракта дистрибутива.

### 7.3 Границы доверия

| Компонент | Привилегии | Почему |
|---|---|---|
| Ядро | полные | минимальный код, аудит, без динамической загрузки стороннего кода |
| model service | чтение весов, большой бюджет памяти/CPU, без прямого доступа к диску и сети | инференс не должен уметь писать файлы |
| plan/intent runtime | вызов возможностей через брокер | изолирует «решения» от «действий» |
| policy engine | только чтение политик, только вердикты | детерминированный, маленький, тестируемый |
| сервисы (httpd/authd/…) | по одной возможности каждый | один сервис — одна функция |
| модель (LLM) | никаких привилегий — генерирует текст/план | это данные, не код |

### 7.4 Память: где живут контексты и знания

Четыре вида памяти — по образцу человеческой, но с машинными гарантиями:

| Вид | Что хранит | Где живёт | Кто пишет |
|---|---|---|---|
| **Рабочая** | KV-cache активной генерации | RAM, закреплённые страницы | движок инференса |
| **Эпизодическая** | транскрипты сессий, события, вызовы возможностей | NVMe, append-only сегменты | управляющий контур |
| **Семантическая** | дистиллированные факты, решения, договорённости + провенанс | NVMe + индекс в RAM | каскад дистилляции (с проверкой) |
| **Процедурная** | каталог возможностей, шаблоны планов, навыки | системный том (read-only) | человек / обновление дистрибутива |

**Почему «просто перечитать историю» не работает.** Prefill на флагманской модели
≈ 44 tok/s: контекст 10 000 токенов — это ≈ 225 секунд только на то, чтобы
«вспомнить» разговор. Поэтому храним не текст, а **состояние**: снапшоты KV-cache
с ключом `(модель, хеш префикса, версия токенайзера, параметры RoPE)` плюс
сегментный лог, из которого при возобновлении читается только хвост.

**Путь возобновления сессии (без перечитывания):**

1. **Парковка.** Грязные KV-страницы дописываются в конец файла снапшота
   (append-only), фиксируется checkpoint с `seq` и CRC.
2. **Возврат.** Читаются только сегменты после checkpoint; KV-страницы мапятся в
   адресное пространство и подгружаются по требованию (read-ahead 2 МБ).
3. **Сборка контекста.** Семантическая память подмешивается retrieval-политикой в
   жёсткий бюджет токенов — детерминированно, без участия модели в решении
   «что читать».
4. **Стоимость возобновления** — секунды чтения NVMe вместо минут prefill.

**Бюджет контекста** (собирается билдером, а не моделью):

| Слот | Бюджет | Источник |
|---|---|---|
| Системная инструкция | ~1k токенов | версия дистрибутива |
| Закреплённые факты (pinned) | ~2k | семантическая память, скоуп сессии |
| Последние ходы | ~8k | хвост транскрипта |
| Извлечённые эпизоды | ~4k | индекс, по запросу |
| Запас | остаток лимита модели | — |

Модель может запросить больше памяти — только через возможность `mem.search`
(под политикой и аудитом), а не «прочитав всё подряд».

Детальный дизайн подсистемы (форматы сегментов и записей, снапшоты KV,
индекс и скоринг, провенанс, жизненный цикл сессии, отказы) —
[`docs/ARCHITECTURE.md`](ARCHITECTURE.md) §5.

**Инварианты, которые нельзя нарушать:**
- транскрипт и снапшот **не переписываются задним числом** (только append + явный
  `forget` с аудитом);
- запись в семантическую память имеет **провенанс**: из какого сегмента, кем
  (модель/человек), когда, с какой уверенностью;
- снапшот KV несовместимой версии модели **инвалидируется**, а не «примеряется»;
- retrieval не вызывает LLM: это индекс + правила (детерминизм, P6).

### 8.15 Долговременная память и контексты

| ID | Требование | Критерий приёмки |
|---|---|---|

| FR-15.7 | Инкрементальный индекс памяти (текст + опционально эмбеддинги), дедупликация по content-addressed чанкам | Новый ход добавляет в индекс только новое; переиндексация всей истории не выполняется |

## 9. Мультиархитектурность и сборка дистрибутива `[РЕШЕНО]`

### 9.1 Целевые платформы

| Арх | Роль | Прошивка/вход | Приоритет |
|---|---|---|---|
| x86-64 | основная (Ryzen 9, AM5, UEFI) | UEFI | MVP, M0–M7 |
| aarch64 | серверы/SoC, дешёвые узлы | UEFI (или DT) | после M4 |
| riscv64 | «свободное железо», будущий силикон | OpenSBI + Device Tree | после M4 |
| кастомный силикон / FPGA | исследовательский и продуктовый горизонт | собственный boot ROM / DT | горизонт, не MVP |

Загрузчик Limine сам поддерживает x86-64/aarch64/riscv64/loongarch64, поэтому порты
получают работающую загрузку почти бесплатно — это важный аргумент в 10.3.

Правило: **x86-64 не должен протекать в ядро**. Всё, что знает про ACPI, APIC,
MSR, порты ввода-вывода, живёт в `arch/x86_64/`. Ядро общается только через
контракт §9.2.

### 9.2 Контракт arch-порта

Порт обязан реализовать (по сути — набор интерфейсов, версионируемых вместе с
ядром):

| Группа | Интерфейс | Что обязан уметь порт |
|---|---|---|
| Boot | `BootInfo` | карта памяти, framebuffer, указатель на прошивочные таблицы (ACPI/DT), cmdline |
| CPU | `CpuOps` | инициализация, SMP bring-up, ID, halt/yield, атомики, барьеры |
| IRQ | `InterruptController` | регистрация обработчиков, EOI, маскирование, MSI(-X) |
| Timers | `Clock` | монотонные тики, программируемые таймеры |
| MMU | `Paging` | маппинг/размаппинг, права, крупные страницы, flush TLB |
| I/O | `PortIo`/`Mmio` | доступ к регистрам устройств |
| SIMD | `SimdOps` | примитивы для нужд **ядра** (копирование, крипто). SIMD инференса — в userspace (`libs/inftk`, бэкенды по арх), иначе каждый matmul требовал бы syscall |
| Debug | `EarlyConsole` | вывод до инициализации драйверов |
| Platform | `PciEnum`, `DeviceTree` | перечисление устройств |

Требования к контракту:
- Всё, что можно выразить портируемо, выражается портируемо; порт — тонкий.
- Каждый порт проходит один и тот же набор тестов (общий для всех арх).
- Добавление арх = реализация контракта + драйверы платформы, без правок ядра.

### 9.3 Сборка и артефакты

```
make image                # образ для текущей/базовой арх
make image ARCH=x86_64    # UEFI-образ (FAT ESP + ядро + сервисы)
make image ARCH=aarch64   # образ для aarch64 (UEFI/DT)
make image ARCH=riscv64   # OpenSBI + kernel + DT
make dist                 # дистрибутив: образ + манифест моделей + подписи + README
```

Артефакт дистрибутива содержит:
1. загрузочный образ (воспроизводимый, с версией и хешем);
2. манифест моделей (какие модели поддерживаются, размер, хеш, лицензия, откуда
   качать);
3. ключи/подписи;
4. документацию и лицензии (свои + сторонних компонентов).

Веса моделей **не входят** в образ (десятки–сотни ГБ): они либо в OCI-подобном
публичном реестре, либо на USB. Манифест — часть дистрибутива, веса — нет.

### 9.4 CI-матрица

| Арх | Сборка | Юнит-тесты | QEMU smoke | Реальное железо |
|---|---|---|---|---|
| x86-64 | обязательно | обязательно | обязательно (q35 + virtio) | ручной прогон на вехе |
| aarch64 | обязательно | обязательно | обязательно (virt) | по возможности |
| riscv64 | обязательно | обязательно | обязательно (virt + OpenSBI) | по возможности |

### 9.5 Чеклист «добавить архитектуру»

1. Реализовать `arch/<arch>/` по контракту §9.2, пройти общие тесты.
2. Добавить `platform/<board>/` (driverы: таймер, консоль, хранилище, сеть).
3. Собрать образ: `make image ARCH=<arch>` — зелёный QEMU smoke.
4. Прогнать бенчмарк инференса, зафиксировать tok/s в отчёте.
5. Обновить CI-матрицу и документацию портов.

Ожидаемая цена порта `[ОЦЕНКА]`: 2–6 человеко-месяцев на арх при готовом ядре
(больше — если ISA/SIMD сильно отличается и нужен свой matmul-бэкенд).

## 10. Варианты и выборы

Для каждого решения: варианты, цена, рекомендация. Рекомендации — предложение,
финальное слово за владельцем (§15).

### 10.1 Модель ядра: как «LLM — ядро» реализуется технически

| Вариант | Плюсы | Минусы | Рекомендация |
|---|---|---|---|
| A. Инференс в ring 0 (kernel-space) | минимум копирований, «модель действительно в ядре» | падение модели = падение системы; невозможно отладить; дыра в безопасности; нельзя обновлять модель без перезагрузки | ✗ |
| B. Привилегированный userspace-сервис с ресурсной политикой (высокий приоритет, зарезервированные ядра/память, крупные страницы) | падение изолировано, модель обновляема, отлаживаема; сохраняет смысл «все ресурсы — модели» | чуть больше накладных расходов | **✓ рекомендация** |
| C. Гибрид: B + «быстрый путь» в ядре для отдельных примитивов (например, копирование KV-cache, SIMD-хелперы) | производительность там, где действительно горячо | сложность, дублирование | позже, точечно, по замерам |

### 10.2 Язык и стек

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Rust (no_std)** | безопасность памяти, кросс-компиляция под все целевые арх, зрелые `x86_64`-крейты и tutorial-база, `core::arch` для SIMD, хорошая эргономика для одного разработчика | не все драйверные паттерны удобны; портирование C-кода (lwIP, ggml) требует FFI или перевода |
| C | максимум референсов, простой FFI, порог входа | 30 лет опыта «как стрелять в ногу»; безопасность и корректность — руками |
| Zig | современная эргономика, comptime, хороший C-interop | экосистема для OS-dev меньше, нестабильность языка |
| C++ | нужен для порта ggml/llama.cpp | freestanding-среда: stdlib нет, всё равно резать |

**Рекомендация:** Rust (`#![no_std]`). Версии на 2026-11-09: Rust stable 1.99.1,
крейты — `x86_64` 0.15.5, `uefi` 0.41.0, `acpi` 6.1.1, `smoltcp` 0.14.0,
`rustls` 0.23.46, `virtio-drivers` 0.13.0, `uart_16550` 0.9.0. Ассемблер — только
arch-примитивы. Крейт `bootloader` 0.11.17 требует nightly — ещё один довод в
пользу Limine (он stable-only). Оговорка: часть фич (`alloc_error_handler`) до сих
пор в Unstable Book, поэтому допустим зафиксированный nightly-тулчейн в
`rust-toolchain.toml`.

Обоснование цифрами: Redox — 43 тыс. строк Rust-ядра за 10 лет командой; SerenityOS
— 151 тыс. строк C++ ядра за 8 лет; Asterinas — ~284 тыс. LOC за 3.5 года командой
10–15 человек. Один человек с Rust и готовыми крейтами реально идёт быстрее в
расчёте на строку, потому что компилятор ловит классы ошибок, на которые в C/C++
уходят недели отладки в QEMU.

Чужой C-код (если понадобится ggml) — только через изолированный FFI-слой, не в
ядре и не в горячем пути системных вызовов.

### 10.3 Загрузчик и SMP bring-up

Ключевой факт: подъём всех ядер на x86-64 (INIT-SIPI-SIPI, trampoline в real
mode, A20, синхронизация MTRR, включение x2APIC) — это **4–6 человеко-месяцев**
отладочной низкоуровневой работы, которая ломается по-разному на каждой
прошивке. И это ровно тот код, который не является идеей проекта.

| Вариант | Что даёт | Чего не даёт | Цена |
|---|---|---|---|
| **Свой UEFI-загрузчик** (Rust + `uefi`) | полный контроль: сам читаешь карту памяти, GOP, `ExitBootServices`, строишь таблицы страниц | нет SMP bring-up, нет парсера ACPI, нет ФС после `ExitBootServices`, firmware-квирки на каждой плате | 2–4 недели до «ядро стартовало» |
| **Limine** v12.9.6 | UEFI+BIOS; x86-64/aarch64/riscv64/loongarch64; HHDM, 4/5-level paging (LA57), framebuffer, RSDP, EFI-memmap, модули, **MP-запрос: сам поднимает все AP и включает x2APIC**, TSC frequency, **entropy**, TPM event log | парсинг MADT/MCFG всё равно наш; нет драйверов и ФС | 1–3 дня до «ядро стартовало» |
| GRUB + multiboot2 | универсальность | UEFI-only среда; legacy-багаж; нет нужных нам запросов | — |

**Рекомендация:** **Limine на MVP**; свой UEFI-загрузчик — отдельная задача после
M4, когда он уже не риск, а замена компонента. Обоснование:

- экономит 4–6 PM — самые дорогие месяцы в этом проекте;
- даёт **мультиархитектурность почти бесплатно** (x86-64/aarch64/riscv64 из
  коробки) — прямое попадание в требование «сборка под разные арх» `[РЕШЕНО]`;
- даёт entropy (нужен для ключей/TLS) и TSC frequency (нужен таймерам);
- ядро остаётся полностью нашим: загрузчик — сменный компонент, а не часть идеи.

Честная оговорка: Limine — чужой код в цепочке доверия (BSD-2-Clause), и «с нуля»
превращается в «ядро с нуля, загрузчик — сторонний». Это решение владельца
проекта: §15, **Q17**.

**Secure Boot.** На AM5 2026 прошивка UEFI class 3, CSM рудиментарен. Отдельно
учесть: сертификаты Microsoft UEFI CA 2011 истекают в июне 2026, идёт массовое
обновление KEK/dbx — ранее подписанный загрузчик может перестать валидироваться.
План: dev-железо — SB выключен; демо-железо — свои ключи (`sbctl`); подпись через
MS UEFI CA (EV-сертификат) не планируем; версия BIOS фиксируется в манифесте
дистрибутива.

### 10.4 Файловая система и хранение весов

| Вариант | Плюсы | Минусы | Цена |
|---|---|---|---|
| Своя минимальная ФС (журнал, CRC) | контроль, проектирование под большие блобы | всё с нуля, включая crash-consistency | 2–4 тыс. строк |
| **Сырой раздел под веса** (extent-карта + манифест SHA-256, чтение напрямую в страницы) | максимальная скорость, минимум кода, идеален для десятков–сотен ГБ | нет «файлов», только блобы моделей | дешевле всего |
| FAT32 (доступ через UEFI) | мгновенный старт | **доступен только пока живы Boot Services** — после `ExitBootServices` его нет; лимит 4 ГБ на файл → для весов непригоден | — |
| EXT4 (порт) | зрелость | JBD2/extents/htree — месяцы работы, наследие Linux | нет |

**Рекомендация:** FAT32 — только ESP (там живёт загрузчик). Системный том — своя
минимальная read-only ФС. Веса — **отдельный сырой раздел NVMe** с extent-картой
и манифестом хешей, чтение напрямую в страницы памяти (заодно самый быстрый путь).
EXT4 не портируем.

### 10.5 Сетевой стек

Измеренная цена «всё своё»: полноценный TCP/IP-стек сопоставимого класса — это
**~58 тыс. строк** (smoltcp: wire 22.5k, socket 17.2k, iface 12.1k, phy 2.5k).
Написать свой минимум — 8–12 тыс. строк и годы краевых случаев (окна, ретрансмиты,
MTU/PMTU, TIME_WAIT, weird-клиенты).

| Вариант | Плюсы | Минусы |
|---|---|---|
| **smoltcp** (Rust, `no_std`) | написан на нашем языке, без C-зависимостей, есть IPv4/ARP/UDP/TCP/DHCP, активно развивается | дизайн без аллокации/событийный — нужно интегрировать с нашим планировщиком и таймерами |
| Свой TCP/IP | полный контроль, обучение | ~8–12 тыс. строк и годы багов; не является целью проекта |
| lwIP (C) | зрелость, компактность, MIT | C-код в Rust-ядре, порт лишнего слоя |
| Без сети в MVP | минимум работы | не закрывает S1: коробка должна отдавать API в сеть |

**Рекомендация:** **smoltcp** как транспорт, свой HTTP/1.1-сервер сверху
(~1.5–3 тыс. строк, JSON — своя минимальная реализация). Написание TCP с нуля —
осознанно вне рамок: это не тот код, за который стоит платить годами отладки.

### 10.6 Инференс-движок

Факты, которые определяют выбор (проверено по исходникам):

- llama.cpp/ggml — MIT, ~541 kLOC. Платформенно-зависимого там немного:
  `llama-mmap.cpp` (916 строк), threadpool в `ggml-cpu.c`, HTTP-сервер (991
  строка). То есть порт «без ОС» = заменить ~5–10 kLOC (mmap → арена, pthread →
  наш планировщик, stdio → блочное устройство, sockets → наш TCP/IP), оставив
  ~216 kLOC ядра llama+ggml-cpu без изменений.
- Свой движок для dense 7–8B — это matmul, attention, RoPE, токенайзер, сэмплер:
  5–15 kLOC на Rust, полностью под нашим контролем.
- Свой MoE (V4-Flash) — не катастрофа: активных параметров 13.2B, маршрутизация
  экспертов проста. Но нужны деквантизация k-/i-quants, токенайзер DeepSeek,
  поддержка архитектуры DeepSeek (MLA/MoE) и prompt caching. Это +6–10 недель.
- SIMD-бэкенды: AVX2 по умолчанию; AVX-512 VNNI/BF16 дают +50–77% на prefill;
  AMX отсутствует у AMD; репакинг весов под AVX-512 (как в ik_llama.cpp)
  заметно ускоряет MoE на Zen 4/5.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Свой движок для dense, затем свой MoE | «написали сами», контроль, чистый Rust, ровно нужные кванты | MoE-архитектура DeepSeek добавляет 6–10 недель; риск не уложиться |
| B. Порт llama.cpp/ggml | MoE, все квантования и скорость — сразу; MIT; проверено тысячами людей | C++ с stdlib/pthread-зависимостями; 216 kLOC чужого кода в сердце проекта |
| C. Свой dense-движок + порт ggml только для MoE | раннее демо, поздний флагман | две кодовые базы, двойная отладка |

**Рекомендация:** вариант A с контрольной точкой после M4. Если свой MoE упирается
в срок — временный порт ggml как «сторонний слой» (с сохранением своего API,
своего планировщика и своего model store), который потом можно выпилить.

**Не портируем вообще** (обоснование физическое/техническое): ROCm и CUDA (нужны
kernel-mode драйверы и Linux-стек), Vulkan compute (нужен GPU-драйвер), AMX (нет
у AMD), NPU XDNA (закрытый рантайм; на Ryzen 9000 его нет), iGPU RDNA2 c 2 CU
(общая ПСП, выигрыша нет).

### 10.7 Доставка модели

Цена TLS измерена: `rustls` — **45.7 тыс. строк** (порт в `no_std` 1.5–3 PM),
`embedded-tls` — 11.1 тыс. строк, свой TLS с нуля — 4–6 месяцев. Поэтому
«скачать LLM по HTTPS при первой загрузке» — самый дорогой из возможных путей:
он тянет TLS + DNS + устойчивый длинный TCP + докачку + кэш.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **HTTP в доверенной LAN + SHA-256 + подпись манифеста Ed25519** | дёшево (0.5–1 тыс. строк), проверяемая целостность и авторство, работает без интернета | требует доверенной сети при первичной доставке |
| USB / второй NVMe с готовым образом весов | детерминированно, оффлайн, быстро | человек с флешкой |
| HTTPS/TLS 1.3 | безопасно в любой сети | 1.5–6 PM и постоянная поверхность атаки |

**Рекомендация:** MVP — **HTTP в LAN + SHA-256 + Ed25519** и USB-путь как
основной оффлайн-сценарий. TLS — только для API (и то как отдельное решение,
см. 10.8/FR-10.3); TLS-клиент для загрузки моделей — после MVP.

### 10.8 Формат API

**Рекомендация:** внешний контракт — OpenAI-совместимый Chat Completions
(клиенты уже есть, SDK работают), плюс собственные админ-эндпоинты и
`/metrics`. Внутренний ABI (возможности, сессии) — свой, не OpenAI.

### 10.10 Память и контексты

| Вариант | Плюсы | Минусы | Цена |
|---|---|---|---|
| A. Только транскрипты + текстовый RAG | просто, знакомая схема | каждый возврат = пересчёт prefill (до 225 с на 10k контекста); история читается заново | дешевле всех |
| **B. Транскрипты + снапшоты KV-cache + дистилляция** | возврат за секунды без prefill; память измерима | снапшот привязан к версии модели/кванта; нужен менеджер бюджета KV | +2–4 PM |
| C. Внешняя memory-служба (отдельный сервис) | можно переиспользовать готовые идеи каскада/провенанса | лишний сервис и протокол; хранилище всё равно нужно своё | +1–2 PM сверх B |

**Рекомендация:** вариант **B**. Идеи каскада «дешёвая модель → проверка основной →
сохранение с провенансом» и учёта экономии токенов уже отработаны в нашем
отдельном проекте памяти для DSH-харнесса — переносим подход, но хранилище,
индекс и политика живут внутри AIOS, а не в внешнем сервисе.

**Открытый вопрос:** снапшоты KV-cache хранят состояние модели, а не только текст.
Это влияет на приватность (в снапшоте можно восстановить сказанное) и на объём
(снапшот может быть сопоставим с размером контекста). Политика хранения — Q19/Q20.

## 11. Не-цели (вне MVP)

- POSIX-совместимость и запуск бинарников Linux.
- GUI/десктоп, браузер, офисные приложения.
- Мультипользовательность, мультитенантность, биллинг.
- Виртуализация, контейнеры, поддержка гостевых ОС.
- Обучение/дообучение моделей, RAG над пользовательскими данными (в MVP).
- GPU/NPU offload: задел в arch-контракте — да, реализация — нет (ROCm/CUDA требуют kernel-mode драйверов и Linux-стека; на Ryzen 9000 нет NPU, а iGPU RDNA2 c 2 CU делит ПСП с CPU и выигрыша не даёт).
- Поддержка произвольного железа: контракт — одна плата.
- IPv6, DNS-сервер, VPN, mesh.
- Кластеризация нескольких узлов.
- Совместимость с docker-образами, k8s, облачные API.

## 13. Дорожная карта

| Веха | Содержание | Критерий выхода (демо) | Оценка `[ОЦЕНКА]` |
|---|---|---|---|
| **M0. Металл** | Limine → ядро; GDT/IDT; paging; физический аллокатор; serial+framebuffer; panic | На реальной AM5-плате грузится и печатает карту памяти, CPUID, ACPI | 2–3 недели |
| **M1. Ядро** | SMP (структуры per-CPU), APIC/x2APIC, вытесняющий планировщик, потоки, свой syscall ABI, ELF-загрузчик, минимальный VFS | 16+ ядер онлайн; два userspace-процесса крутятся и общаются через IPC | 8–14 недель |
| **M2. Хранилище** | NVMe-драйвер (~1.3 тыс. строк по образцу Redox), своя ФС с журналом, сырой раздел + манифест весов, **append-only лог сессий** | Читаем 40 ГБ блоб ≥ 1 ГБ/с, хеш совпал; обрыв питания не ломает ФС; сессия переживает перезагрузку | 8–12 недель |
| **M3. Сеть** | драйвер одного NIC, smoltcp, DHCP, свой HTTP/1.1-сервер | `curl` с другой машины получает JSON; порт-скан видит только нужное | 10–16 недель (главный риск — реальный NIC) |
| **M4. Инференс** | свой движок dense 7–14B, SIMD по арх, токенайзер, KV-cache, сэмплер, SSE-стриминг, OpenAI-совместимый API, **снапшоты KV и парковка сессий** (цель — 14B Q4 ≥ 6 tok/s, 32B Q4 ≥ 3 tok/s) | `/v1/chat/completions` стримит токены; возврат к запаркованной сессии ≤ 2 с без prefill; tok/s и TTFT в отчёте | 12–20 недель |
| **M5. Провижининг** | first boot: DHCP → загрузка модели по LAN/USB → SHA-256 + Ed25519 → установка → старт; A/B обновления | Чистый диск + питание → работающий API без ручных шагов | 6–10 недель |
| **M6. Управляющий контур** | каталог возможностей, plan runtime, policy engine, аудит, подтверждения; консоль; **дистилляция памяти и retrieval-политика** | «Перезапусти сервис, покажи метрики, объясни почему упало» — моделью с аудитом; повторный вопрос опирается на память, а не на перечитывание | 10–16 недель |
| **M7. Портативность** | порт aarch64 и/или riscv64 в QEMU, CI-матрица, `make dist` | `make image ARCH=aarch64` + зелёный smoke, тот же эталонный ответ модели | 12–20 недель |
| **M8. (горизонт)** | свой UEFI-загрузчик вместо Limine; MoE (V4-Flash); GPU-offload; собственный силикон | — | вне MVP |

**Две оценки, и они расходятся — это нормально и важно.**

1. Сумма по вехам `[ОЦЕНКА]` — **~70–110 недель** одного инженера (16–26 PM).
   Это оптимистичный сценарий «если всё пойдёт по плану».
2. Независимая модель по объёму кода (800–1300 отлаженных строк низкоуровневого
   кода в месяц; якоря — Redox kernel 43 тыс. строк за 10 лет, SerenityOS kernel
   151 тыс. строк за 8 лет, seL4 8.7 тыс. строк за 25 человеко-лет) —
   **30–45 человеко-месяцев до MVP-демо**: команда 4–6 низкоуровневых
   инженеров — 9–12 месяцев, один человек — 2.5–4 года.

Расхождение в 1.5–2 раза — историческая норма для низкоуровневых проектов.
**Планировать надо по второй цифре**, а первую использовать как контроль: если
веха вылезает за оптимистичную оценку вдвое — значит реализуется не тот сценарий.

Самое недооцениваемое (по замерам, не по ощущениям): порт инференс-движка
(8–15 PM при варианте с ggml), реальный NIC (3–8 PM), TLS (1.5–3 PM даже с
rustls), SMP без готового загрузчика (4–6 PM вместо 1–1.5).

Честная оценка до «полного продукта S1 с MoE» — годы; поэтому MVP намеренно dense.

Порядок неслучаен: M0–M1 дают «своё ядро», M2–M3 — «система живая», M4 —
«модель работает», M5 — «это appliance», M6 — «это AIOS, а не просто сервер»,
M7 — «портативность доказана».

## 16. Глоссарий

| Термин | Значение в AIOS |
|---|---|
| **Управляющий контур** (control plane) | Цикл «намерение → план → политика → исполнение → отчёт», ядро идеи проекта |
| **Возможность** (capability) | Типизированное действие системы, которое модель может запросить (`fs.read`, `svc.restart`) |
| **Каталог возможностей** | Версионируемый список всех возможностей с описанием — «API системы для модели» |
| **Policy engine** | Детерминированный компонент, разрешающий/запрещающий вызовы возможностей |
| **Сессия** | Единица работы пользователя (человека или клиента API): права, бюджет, история, аудит |
| **Model store** | Хранилище весов моделей с манифестом, хешами и подписями |
| **HAL/arch-порт** | Граница портируемости: контракт §9.2 и его реализация под конкретную ISA/платформу |
| **Дистрибутив** | Артефакт сборки: образ + манифест моделей + подписи + документация |
| **Appliance** | Машина, которая включается и сразу отдаёт API; без администрирования человеком |
| **Model service** | Привилегированный userspace-процесс, владеющий весами и KV-cache |
