# AGENTS — правила работы в AIOS

Корневые правила для всех, кто работает в этом репозитории: оркестратора,
исполнителей, ревьюверов, тестировщиков. Файлы `AGENTS.md` в подпапках дополняют
этот, но не отменяют.

---

## 1. Что мы делаем

**AIOS** — операционная система, написанная с нуля, в которой LLM является
управляющим контуром системы. Не Linux-клон, не надстройка: своё ядро, свой ABI,
своя файловая система, свой сетевой стек. Модель управляет системой через
консоль и защищённый API, но **не имеет прав**: она предлагает, ядро разрешает
(каталог возможностей → policy engine → аудит).

Стек: Rust `no_std`, x86-64 + UEFI (загрузчик Limine), далее aarch64/RISC-V.
Целевое железо MVP: Ryzen 9, 64 ГБ DDR5, NVMe.

**Читать перед любой задачей:**

| Документ | Что внутри |
|---|---|
| [docs/SPECIFICATION.md](docs/SPECIFICATION.md) | концепция, 68 требований с критериями приёмки, варианты, риски, вопросы Q1–Q23 |
| [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) | ядро, ABI, форматы памяти, ADR, первый срез |
| [docs/PLAN-M0.md](docs/PLAN-M0.md) | задачи вехи M0 (что делаем сейчас) |
| [docs/WORKFLOW.md](docs/WORKFLOW.md) | ветки, слияния, релизы |

Текущая веха — **M0 «Металл»**: ядро грузится в QEMU, печатает карту памяти,
ACPI, CPUID; есть физический аллокатор, paging, куча, лог; всё проверяется в CI.

## 2. Git: как мы работаем

| Ветка | Назначение | Кто пишет | Куда сливает |
|---|---|---|---|
| `main` | релизы | никто напрямую | из `develop` после проверенного дистрибутива |
| `develop` | интеграция | никто напрямую | из `v0.1`, когда версия готова |
| `v0.1` | **ветка версии — вся разработка** | оркестратор (слияния) | — |
| `task/<ID>` | одна задача = одна ветка = один worktree | один исполнитель | в `v0.1` через оркестратора |

Жёсткие правила:

1. **Исполнитель работает только в своём worktree** `worktrees/<ID>` на ветке
   `task/<ID>`. Основной чекаут и чужие worktree не трогать.
2. **Пуш — только своей ветки задачи.** В `v0.1`, `develop`, `main` пушит
   оркестратор или человек. Пуш в `main` запрещён всегда.
3. **Коммит:** `[<ID>] Кратко, что сделано` + тело: зачем, что проверено, какие
   числа получились. Один коммит — одна законченная мысль.
4. **Слияние** делает оркестратор: `git merge --no-ff task/<ID>` в `v0.1`.
   Исполнитель не сливает сам.
5. **Конфликт:** в файлах задачи — решает исполнитель, в общих файлах
   (`Cargo.toml`, `rust-toolchain.toml`, `.cargo/config.toml`, `AGENTS.md`) —
   только оркестратор.
6. Общие файлы правит только оркестратор. Нужно изменение — напиши в отчёте
   карточки, не коммить сам.

## 3. Доска задач (kanban)

Источник истины — карточки `.kanban/tasks/<ID>.md`. Ветка задачи наследует
карточку, исполнитель работает с её копией в своём worktree.

Статусы и переходы:

```
backlog ──(асайн с --owner)──▶ todo ──(взял в работу)──▶ in-progress ──(сдал)──▶ in-review
                                                                                   │
                              in-progress ◀──(вернул)──────────────────────────────┤
                                                                                   ▼
                              testing ◀──────────────────────────────(принял)
                                 │
                    ready ◀──────┴────(вернул)──▶ in-progress
   любой статус ──▶ blocked (нужен человек) ──▶ in-progress
```

Инструменты (в `bin/`):

```bash
bin/task-move.sh <ID> in-progress                # исполнитель взял задачу
bin/task-move.sh <ID> in-review --note "…"       # сдал на ревью
bin/task-move.sh <ID> testing  --note "…"        # ревьювер принял
bin/task-move.sh <ID> ready    --note "…"        # тестировщик принял
bin/board-status.sh                              # что на доске сейчас
```

**Правила ролей:**

| Роль | Что делает | Что не делает |
|---|---|---|
| `dispatcher` (оркестратор) | режет задачи, асайнит, вливает ветки, развязывает конфликты | не пишет код задач |
| `worker` | берёт свою карточку в `in-progress`, делает, сдаёт в `in-review` | не ревьюит себя, не сливает ветки |
| `reviewer` | `in-review` → `testing` (принял) или → `in-progress` (вернул с замечаниями) | не правит код задачи вместо автора |
| `verifier` | `testing` → `ready` (принял) или → `in-progress` (вернул) | не ревьюит код, проверяет поведение |

Одна карточка `in-progress` на исполнителя. Взял задачу — двигай статус сам,
не жди оркестратора. Вернули с замечаниями — исправь и сдай снова, с отчётом.

## 4. Код

- Rust `no_std` для ядра; сервисы — тоже `no_std` (свой рантайм).
- Сборка ядра: `PATH="$HOME/.cargo/bin:$PATH" cargo build --target x86_64-unknown-none`.
  В PATH первым стоит Homebrew-cargo без cross-target — **всегда используй
  `$HOME/.cargo/bin/cargo`**.
- Тесты форматов/логики — на хосте обычным `cargo test`, без QEMU.
- Запуск: `make qemu` (QEMU 11.1.3, OVMF `/opt/homebrew/share/qemu/edk2-x86_64-code.fd`).
- Новые зависимости — только с согласия оркестратора (каждая ломает no_std или
  тащит лишний код).
- Не писать в прошивку/NVRAM, не трогать чужие разделы диска.

## 5. Определение готовности (definition of done)

Задача сдаётся в `in-review` только когда:

1. код собирается (`cargo check --target x86_64-unknown-none` и/или `cargo test`);
2. критерий приёмки из карточки **проверен**, а не «должно работать»;
3. номер и результат проверки записаны в отчёте карточки (`--note`);
4. коммит в ветке задачи, сообщение по формату `[<ID>] …`;
5. документ обновлён, если поведение поменялось (спека/архитектура/план).

Ревьювер и тестировщик проверяют **критерий из карточки**, а не стиль. Вернули —
пишут конкретно: что не сходится, чем воспроизвести, что ожидалось.

## 6. Границы помощи

- Вопрос по существу — в отчёт карточки (`--note`) и в сессию оркестратора.
  Не выдумывай требования: если в карточке и документах ответа нет — это
  `blocked`, а не «сделаю по-своему».
- Менять архитектуру (ADR) может только владелец проекта через оркестратора.
- Токены и время дороги: не переписывай то, что работает, и не расширяй задачу.

## 7. Язык

Документы и карточки — по-русски. Код, имена, комментарии в коде — по-английски.
Отчёты в карточках — по-русски, кратко и с числами.
